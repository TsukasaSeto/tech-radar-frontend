### 2. `_seen.json` コミット直前チェック（`git diff --cached | grep '^-  "'`）が末尾要素への追記で必ず偽陽性を出す
- **種類**: ツール / プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > 削除禁止ルール」Step 5（commit直前の確認）
- **詳細**: 新規URLを配列末尾に追記すると、旧配列の最後の要素（カンマなし）が新配列では最後ではなくなり `,` が付与される。そのため生JSONの行単位diffでは当該行が「削除+追加」として現れ、`grep '^-  "'` に必ずマッチする（本日は `"https://stripe.com/blog/meet-stripes-knowledge-ai-platform"` → `"https://stripe.com/blog/meet-stripes-knowledge-ai-platform",` の1件がこれに該当）。Step 2-3で行ったURL集合のsort比較（`jq -r '.[]' | sort` の差分）では実際の削除が0件であることを確認済みで、これは書式起因の偽陽性だった。
- **影響**: Step 5のチェックが「必ず1件は引っかかる」状態になっており、本来検出すべき「本当の削除」との区別が機械的にできない（今回は目視で末尾カンマ差分と確認したため実害はなかったが、確認を怠ると誤ってコミットを中止したり、逆に本物の削除を見逃したりするリスクがある）
- **再現性**: 継続的（配列に1件でも追記すれば毎回発生する構造的な問題）
- **プロンプト改善提案**:
  - **対象セクション**: 「`_seen.json` の仕様 > 削除禁止ルール」Step 5
  - **現状の記述**: `git diff --cached _seen.json | grep '^-  "'`
  - **提案する変更**: 生diffではなく「削除された行からカンマを除いた文字列が、追加された行にも同じURLとして存在するか」を無視するロジックにする。例えば `jq -r '.[]' _seen.json | sort > /tmp/new-sorted.txt && jq -r '.[]' <(git show :_seen.json) | sort > /tmp/staged-old-sorted.txt` の比較（Step 2-3で既に使っている sort 比較）を commit 直前チェックとしてもそのまま再利用し、生diffのgrepは廃止する
  - **理由**: 現状のgrepチェックは末尾要素への追記時に構造的に偽陽性を出すため、Step 2-3の意味的チェックと矛盾するシグナルを出してしまう。同じsort比較ロジックに統一すれば偽陽性がなくなり、本当の削除だけを検出できる
  - **想定リスク**: なし（既存のsort比較ロジックを再利用するだけ）
  - **優先度**: 中

### 2. 出典引用がプロンプトの主張と噛み合わないパターン1c候補の扱いが不明確

- **現状の記述**: 「原文引用1-2行を必須」「ルール本文に記事からの引用を含める」
- **提案する変更**: 引用は「地の文の1-2行」に限定せず、「記事が示すコード例・設定例そのもの」でも代替可能である旨を明記する（例: 「原文引用は地の文の1-2行、または記事が示す設定/コード例の該当箇所のいずれかでよい」）
- **理由**: 本日、Tailwind CSS v4 の `@theme` 自己参照命名という具体的でパターン1c相当の技術的知見（コード例あり）を含む記事があったが、記事の主眼（「design.mdを作らない」という個人の意思決定プロセス）についての地の文しか直接引用できる文がなく、技術的知見そのものを裏付ける1-2行の地の文が見つからなかったため採用を見送った。コード例自体が公式仕様の直接的な証拠になるケースでは、地の文の引用に固執すると有効な知見を落とす
- **想定リスク**: 「コード例があれば引用不要」という運用に緩めすぎると、コードの解釈がRoutine（このセッション）の独自解釈になり「実際に読んだ記事」の裏付けが弱くなる可能性がある。コード例を引用する場合も、それが記事内の実際のコードそのままであることの確認は必須とすべき
