### 5. `_seen.json` commit直前チェック（`grep '^-  "'`）が整形起因で偽陽性になる
- **種類**: ツール / プロンプト記述
- **発生箇所**: `_seen.json` の仕様 > 削除禁止ルール > 手順5（commit 直前の確認）
- **詳細**: 既存 `_seen.json` はインデント2スペース・末尾カンマなしの pretty-print JSON。新規 URL を末尾に追記すると、旧・最終行（末尾カンマなし）に新しくカンマを付与する変更が必ず発生し、その行は diff 上で `-  "https://...元の最終行..."` → `+  "https://...元の最終行",` という「削除+追加」として現れる。手順5の `grep '^-  "' && exit 1` はこれを額面通り「URL削除」として誤検知する。
- **影響**: 今回は手順3（sorted URL 比較による包含チェック）と目視確認で「該当 URL は新ファイルにも存在する」ことを確認した上でコミットを続行した。手順5を機械的に絶対視すると、正当な append 操作のたびに毎回コミットが止まる。
- **再現性**: 継続的（末尾カンマなし pretty-print の JSON に append する限り、末尾に達するたびに必ず発生する構造的な偽陽性）
- **提案**: 下記「プロンプト改善提案 3」参照

- **理由**: 今回の実行で判明した通り、1セッションで56フィード全てを本文精読まで含めて処理しきるのは時間的に厳しく、後半のタグ（Medium の大半）が未実施のまま終了した。ローテーション化すれば「今日どのタグを見たか」が明確になり、silent な欠落を防げる

### 3. commit直前チェックを「行diff」ではなく「集合比較」に変更する
- **対象セクション**: `_seen.json` の仕様 > 削除禁止ルール > 手順5
- **現状の記述**: `git diff --cached _seen.json | grep '^-  "' && { echo "ERROR..."; exit 1; }`
- **提案する変更**: 手順3で既に行っている `diff <(sort base) <(sort new) | grep '^<'` による集合比較を最終チェックとしても再利用し、手順5の行ベース grep は廃止する（あるいは「削除された行のURLが新ファイルのどこにも存在しない場合のみエラー」に変更する）:
  ```bash
  git show HEAD:_seen.json 2>/dev/null | jq -r '.[]' | sort > /tmp/committed-before.txt
  jq -r '.[]' _seen.json | sort > /tmp/committed-after.txt
  diff /tmp/committed-before.txt /tmp/committed-after.txt | grep '^<' && { echo "ERROR: URL deletion"; exit 1; }
  ```
- **理由**: 現行の行ベース grep は「末尾カンマの付け外し」のような無害な整形差分を「削除」と誤検知する（観察した問題5参照）。集合比較なら真の削除のみを検知できる
- **想定リスク**: なし（手順3と同じロジックを再利用するだけ）
- **優先度**: 中
