### 1. 定義済みソース数とプロンプトの「21/24ソース」表記が大きく乖離している
- **種類**: プロンプト記述
- **発生箇所**: 「絶対ルール3」「標準RSSソース定義（24ソース）」見出し、changelog テンプレの「取得統計（21ソース）」
- **詳細**: 「標準RSSソース定義（24ソース）」は実際には Zenn 15トピック + Qiita 14タグ + dev.to 15タグ + Medium 12タグ + 公式6 + 国内9 + 海外4 = 75 フィード + Stripe HTML 1 = 76ソースをタグ/トピック単位で数えると存在する。ドメイン単位（zenn.dev, qiita.com…のような「サイト」単位）で数えれば24前後になるが、実際にfetchすべき単位は「フィードURL」であり、この数え方の齟齬がプロンプト全体の分量見積もりを大きく誤らせている。
- **影響**: 今回の実行で1回のセッション内に76ソース全ての段階1〜5フォールバック＋個別記事の段階A〜Cを処理しきれず、42ソース（全体の55%）が未着手のまま終了した。「21/24ソース」という表記を信じて時間配分すると、実際の3倍以上のソースが残っていることに気づきにくい。
- **再現性**: 単発（今回セッションの実行方式に依存する可能性はあるが、ソース定義自体の数え方の齟齬はプロンプト固有の問題）

### 2. `_seen.json` の実ファイル形式が仕様セクションと異なる
- **種類**: プロンプト記述
- **発生箇所**: 「_seen.json の仕様 > スキーマ」セクション
- **詳細**: プロンプトは `{"version": "1.0", "updated_at": "...", "entries": [{"url":..., "fetched_at":..., "status":...}]}` という object 形式を規定しているが、リポジトリの実際の `_seen.json` は **文字列URLのフラット配列**（`["https://...", "https://...", ...]`）であり、`status`（adopted/read_skipped/fetch_failed の区別）を一切保持していない。過去のコミットメッセージ（`chore: update _seen.json with N new URLs`）を見る限り、この配列形式が実際の運用慣習として定着している。
- **影響**: 「24時間以内の fetch_failed は再試行可能」「90日超のエントリは別Routineで削除」といった `status`/`fetched_at` に依存するロジックが実データ上は実行不可能（該当フィールドが存在しない）。今回は既存の配列形式に合わせて2件のURLのみ追記した。
- **再現性**: 継続的（過去の changelog のコミット履歴からも一貫して配列形式が使われていると推測される）
- **想定される次アクション**: プロンプトの `_seen.json` 仕様セクションを実際のフラット配列形式に合わせて書き換えるか、逆に実データを object 形式へ移行するかを人間が判断する必要がある。

### 3. Snyk Blog の WebFetch サブモデルが日付判定で自己矛盾した回答を返した

## プロンプト改善提案（3件）

### 1. ソース数表記をフィード単位の実数に修正する
- **対象セクション**: 「絶対ルール3: 経路統計テーブルを必ず記載」の見出し例、「標準RSSソース定義（24ソース）」見出し
- **現状の記述**: `## 取得統計（21ソース、成功 N / 失敗 M）` / `## 標準RSSソース定義（24ソース）`
- **提案する変更**: 見出しを「標準RSSソース定義（サイト単位24、フィード単位76）」のように両方明記し、changelog テンプレの取得統計見出しも `## 取得統計（{実際に定義されているフィード総数}ソース）` と実数を算出させる指示に変える
- **理由**: 今回、表記上の「21/24」を鵜呑みにして時間配分した結果、実際は76ソースあり55%が未着手に終わった。数え間違いに気づけるようにするため
- **想定リスク**: 特になし（表記の正確化のみ）
- **優先度**: 高

### 2. `_seen.json` 仕様を実データ（フラット配列）に合わせて書き換える
- **対象セクション**: 「_seen.json の仕様 > スキーマ」
- **現状の記述**: object 形式（`version`/`updated_at`/`entries[].status`）を規定
- **提案する変更**: 実際に運用されているフラット配列形式（`["url1", "url2", ...]`）を正としてスキーマ節を書き換え、`status` 別再試行ロジック（24h以内のfetch_failedは除外等）を「配列形式では追跡不可能」と明記するか、あるいは今後 object 形式へ移行する場合の一括マイグレーション手順を別途起票する
- **理由**: 現在プロンプトが規定する再試行ロジックの一部が実データ上意味をなしていない
- **想定リスク**: object形式への移行を選ぶ場合、既存2000件超のURLの一括変換PRが必要になり、`_seen.json` の削除禁止ルール（4段階diff検証）との整合を取る追加検証が要る
- **優先度**: 中

### 3. 1回のRoutine実行で処理しきれない場合の「優先順位付け」を明示する
- **対象セクション**: 「アクセス経路の絶対指示」以降、Step 4 の直前
- **現状の記述**: 全ソースを同列に扱い、優先順位の指定がない
- **提案する変更**: 「時間制約に直面した場合、公式ソース（Next.js/Vercel/Sentry/Snyk/GitHub Blog/OWASP）と主要トピック（nextjs, react, typescript, security, ai-agent）を優先し、それ以外は後回しにする」という優先順位リストを追加する
- **理由**: 今回はある程度直感的に公式ソース→主要トピックの順で着手したが、明文化されていないため実行ごとにばらつきが出る可能性がある
- **想定リスク**: 優先度の低いトピック（css, i18n, accessibility等）が構造的に手薄になり続けるリスクがあるため、「N回に1回は優先度の低いトピックを先に着手する」等のローテーション策も併記した方がよい
- **優先度**: 中
