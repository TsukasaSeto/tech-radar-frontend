### 1. Knowledge Work Developers Blog（note.com）が egress proxy でドメイン単位ブロックされており、フォールバック段階3〜4も同一プロキシ経由のため無意味だった
- **種類**: アクセス / 実行環境
- **発生箇所**: Step 4 標準RSSソース（ナレッジワーク Developers Blog、note.com/knowledgework/rss）
- **詳細**: 段階1で `note.com` への直接アクセスが `EGRESS_BLOCKED`（プロキシによるドメイン単位の遮断）で失敗した。この場合、段階3（AllOrigins raw）・段階4（AllOrigins get）を試しても `api.allorigins.win` 経由で `note.com` を取得しようとした結果 HTTP 500 が返り続け、結局失敗に終わった。さらに段階5相当として試した `r.jina.ai` 経由の取得も `EGRESS_BLOCKED` だった。`EGRESS_BLOCKED` は他ソース（Stripeの `stripe.dev`）でも観測されており、これは「サイト側の403/522」とは性質が異なる「実行環境のプロキシ許可リスト外」のエラーである。プロキシ許可リストに乗っていないドメインは、AllOrigins のような別ドメイン経由のプロキシを試みても、その先で同じ`note.com`のコンテンツを取得しようとする限り、リモート側の問題（今回は500）で結局失敗しやすい。

- **プロンプト改善提案**:

  - **想定リスク**: なし（分類の明確化のみ）

### 3. `_seen.json` の削除検知に使う `git diff | grep '^-  "'` は配列末尾要素の追記時に偽陽性を出す
- **種類**: ツール / `_seen.json` 安全性チェック手順
- **発生箇所**: `_seen.json` の commit 前チェック（CLAUDE.md 記載の手順）
- **詳細**: 新規URLを配列末尾に追記すると、従来の末尾要素の行が「カンマなし」から「カンマあり」に変わるため、その1行が `diff` 上で `-`（削除）＋`+`（追加）の対として現れる。今回のケースでは `git diff --cached _seen.json | grep '^-  "'` が `https://zenn.dev/dentyu/articles/animate-skeleton-with-view-transition` の行にヒットしたが、これは同じURLが `+` 側にも（末尾カンマ付きで）存在しているだけで、実際の削除ではなかった。念のため `comm -23 <(ソート済み旧URL一覧) <(ソート済み新URL一覧)` による集合ベースの比較を別途行い、実削除が0件であることを確認した上でコミットした。
- **影響**: 実害なし（今回は集合ベースの二重チェックで確認済み）。ただし、行ベースのgrepだけを信じるフローだと、末尾要素の追記のたびに「削除の疑いあり」という偽陽性アラートが出て、毎回手動確認が必要になる。逆に言えば、行ベースのgrepは「本当の削除」を検知する保証もない（削除されたURLが別の行のカンマ付近に偶然一致しない限り検知できるが、複数削除・複数追加が同時に起きるケースでは見落としうる）
- **再現性**: 配列末尾に追記する運用である限り、原理的に毎回発生しうる
- **プロンプト改善提案**:
  - **対象セクション**: CLAUDE.md「`_seen.json` の URL 削除禁止」の検証手順、および `suggested_commands`（`.serena/memories/`）記載の削除検知コマンド
  - **現状の記述**: `git diff --cached _seen.json | grep '^-  "'` を削除検知の主手段としている
  - **提案する変更**: 主手段を集合ベースの比較（`jq -r '.[]' base | sort` と `jq -r '.[]' new | sort` を `comm -23` で比較）に変更し、行ベースの `grep '^-  "'` は補助的な目視確認に留める、と明記する
  - **想定リスク**: なし（より正確な検証方法への置き換え）
  - **優先度**: 中
