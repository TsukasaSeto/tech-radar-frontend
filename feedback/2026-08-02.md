## 観察した問題（3件）

### 1. `_seen.json` の実ファイルスキーマとプロンプト記載スキーマの乖離が、10回以上報告済みで依然未修正
- **種類**: プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > スキーマ」セクション
- **詳細**: プロンプトは `{"version": "1.0", "updated_at": ..., "entries": [{"url", "fetched_at", "status"}, ...]}` という object スキーマを記載しているが、実際の `_seen.json`（origin/main時点、2270件）は URL 文字列のみのフラット配列だった。`feedback/` を grep すると、この乖離は少なくとも 2026-05-29, 06-30, 07-01, 07-03, 07-05, 07-08, 07-10, 07-19, 07-25, 07-26, 07-30 の11回にわたって既に報告されている。実害は今回もなかった（「削除禁止ルール」セクションの jq コマンド例自体はフラット配列前提で書かれており、実態と一致しているため）が、v12 になっても本文中のスキーマ記載自体は書き換えられていない。
- **影響**: 実害なし（毎回、実行側が「フラット配列が正」と判断して処理している）。ただし `status`（adopted/read_skipped/fetch_failed）による重複読み防止という設計意図が実装に存在しないため、「今日読んで却下した記事」と「まだ一度も読んでいない記事」を `_seen.json` 単体では区別できない状態が続いている。
- **再現性**: 継続的・11回目の報告
- **プロンプト改善提案**:
  - **対象セクション**: 「`_seen.json` の仕様 > スキーマ」
  - **現状の記述**: object + `entries[].status` 形式のスキーマ例
  - **提案する変更**: 実態に合わせてフラット配列スキーマ（`["url1", "url2", ...]`）に書き換える。`status` の区別が必要なら別ファイル（例: `_seen_status.json` や changelog 側のみ）で持つ設計に変更するか、あるいは「`status` 区別は運用上不要と判断し、read_skipped/fetch_failed も単に『既読』として同列に append する」という現行の実運用をそのまま仕様として明文化する
  - **理由**: 11回同じ指摘が繰り返されているのに本文が更新されないのは、feedbackが「読まれていない」か「意図的に据え置かれている」かのどちらかだが、いずれにせよ次回以降の実行者が同じ確認作業を毎回繰り返すコストが積み上がっている
  - **想定リスク**: なし（ドキュメント修正のみ）
  - **優先度**: 高（11回目のため）

### 2. dev.to/Medium は `webdev`/`ai` タグ以外でも個人ブログの雑記・広告記事が大半を占める
- **種類**: 採用基準
- **発生箇所**: Step 4（標準RSSソース取得）、dev.to `css`/`accessibility`/`performance`/`security`、Medium 全般
- **詳細**: プロンプトは dev.to の `webdev`/`ai` タグのみを名指しして「パターン2を厳格適用」と警告しているが、今回の36h窓では `css`（CSS Art作品の紹介記事多数）、`security`（DMARC/SPF等メール認証の個人ブログ）、`performance`（無関係な話題: CPU温度・QUIC解説・Docker基礎）、Medium 全タグ（コース受講記・キャリアポエム・仮想通貨・料理アプリ等）でも同様に技術的に無関係またはトーンが個人日記的な記事が候補の大半を占めた。厳密な件数はカウントしていないが、体感で候補の8割以上がこのパターン。
- **影響**: 今回はタイトルベースのフィルタリングで実質的に除外できたため実害はなかったが、候補一覧が肥大化し、有望な記事を14件に絞り込む判断コストが増える
- **再現性**: 不明（過去feedbackで明示的に言及されているか未確認だが、プロンプト側の記述が2タグのみに限定されている点は今回初めて明確に「不足している」と感じた）
- **プロンプト改善提案**:
  - **対象セクション**: 「dev.to の `webdev` / `ai` タグ注意」の直後
  - **現状の記述**: `webdev` / `ai` タグのみへの注意書き
  - **提案する変更**: 「dev.to/Medium は上記2タグに限らず全体的に個人ブログの雑記・広告・無関係トピックの比率が高い。タイトルから技術的практика抽出が見込めるか一次フィルタしてから、個別記事の本文取得（段階A以降）に進むこと」という一般的な注意を追記する
  - **想定リスク**: 過度なフィルタで見逃しが増える可能性（ただし現状は逆に候補過多で選定コストが高い状態）
  - **優先度**: 低

### 3. サブエージェント経由の WebFetch が、原文の直接引用ではなく要約・パラフレーズを返すことがあった
- **種類**: ツール
- **発生箇所**: 個別記事の本文取得フェーズ（"French Localization Broke Our Layout" 記事）
- **詳細**: 該当記事の原文引用を3回試みたが、2箇所目以降はいずれも要約された文章が返り、原文そのままの1-2行を確定できなかった（1箇所目のみ確定）。本Routine自体はこの記事を不採用としたため実害はなかったが、もし採用判定に進んでいた場合、プロンプトが必須とする「原文引用1-2行」の要件を満たせない状態でルール化してしまうリスクがあった。
- **影響**: 実害なし（今回は不採用のため）
- **再現性**: 単発観測
- **プロンプト改善提案**:
  - **対象セクション**: 「絶対ルール1: モデル知識でルールを作らない」内、原文引用の必須化部分
  - **現状の記述**: 「原文引用1-2行を必須」とあるが、取得手段（WebFetch）が要約を返した場合の扱いが未定義
  - **提案する変更**: 「WebFetch の結果が要約・パラフレーズであり原文そのままの引用を確定できない場合、その記事は原文引用が取れるまで再取得を試みるか、取れなければ採用を見送る（B強化であっても出典引用ブロックには原文一致が必要）」という運用ルールを明記する
  - **想定リスク**: なし
  - **優先度**: 低
