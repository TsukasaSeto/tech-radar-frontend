### 2. dev.to の nextjs/react タグで単一著者による同日大量投稿（コンテンツファーム的傾向）を観測
- **種類**: 情報源の質の傾向
- **詳細**: `dev.to/feed/tag/nextjs` の窓内8件中7件、`dev.to/feed/tag/react` の窓内5件中4件が同一著者 `daniel_pertu` による同日（2026-09-15 19時台）連続投稿だった。内容は同一プロダクト（QRコード注文アプリ）の実装小ネタを1テーマ1記事に切り出したもので、個々の記事はNext.js公式機能（`next/og`、Vercelの`x-vercel-ip-country`ヘッダー等）に言及しコード例もあるが、(1) 単著のため採用基準のPattern 2（2名以上の独立著者）を満たさない、(2) Pattern 1c として扱うには公式機能の検証というより個人プロダクトの設計エッセイ色が強い、と判断し全件見送った。
- **想定リスク**: 既知の `dev.to webdev/ai` タグの低品質傾向（2026-09-07/09-09 feedbackで既出）とは別に、`nextjs`/`react` タグでも同種の「同一著者による大量投稿で埋まる」現象が起き得ることが新たに確認された。プロンプトの pattern-2 運用基準（"cross-posts by the same author count once"）は複数記事にまたがる同一テーマの判定には有効だが、同一著者が「別テーマの複数記事」を大量投稿した場合の扱い（時間浪費を避けるための打ち切り基準）は明文化されていない。
- **提案する変更**: dev.to の個別タグで「直近ウィンドウの新着のうち著者数が1名のみ」の場合、2件目以降の同著者記事は本文精読をスキップしてよいというショートカット基準をプロンプトに追記すると、限られた時間予算をより多くの情報源のstage-1網羅に振り向けやすくなる。
- **優先度**: 低〜中

### 3. WebFetch がRSS/Atomの `<pubDate>`／`<published>` から時刻情報を欠落させることがある
- **種類**: ツールの制約
- **詳細**: WebFetch はHTMLをMarkdown化して小型モデルで要約する方式のため、フィードの日付を「YYYY-MM-DD」まで返し、時刻（時分秒・タイムゾーン）を省略する場合があった（例: Zenn nextjs フィードの1回目の呼び出し）。36h窓の境界判定（例: cutoff `2026-09-14T09:07:10Z` ちょうど付近の記事）には日付だけでは不十分で、2回目以降のプロンプトで明示的に時刻を要求することで改善したが、毎回明示しないと欠落するリスクがある。
- **提案する変更**: プロンプトのFallback chain節に「WebFetchで一覧取得する際は、プロンプトに『発行時刻をタイムゾーン込みで含めること』を必ず明記する」という一文を追記する。
- **優先度**: 中

### 4. `_seen.json` の削除検知チェックが実際のスキーマ（フラット配列）でコメントアウト付きコマンド通り false positive を起こす
- **種類**: プロンプト仕様とリポジトリ実態の齟齬
- **詳細**: `_seen.json` は仕様書に記載された `{version, entries:[{url,...}]}` 形式ではなく、実際には URL 文字列のフラット配列（`["url1", "url2", ...]`、4184件）だった。仕様書自体「(adapt to the actual top-level schema...)」と明記しており今回はそれに従いフラット配列用の集合ベース dedup（`jq` の `reduce` で `.url` ではなく配列要素そのもので重複排除）に読み替えて実施した。一方、コミット直前の最終チェック `git diff --cached _seen.json | grep '^-  "url"'` は entries オブジェクト形式を前提にしたパターンのため、フラット配列にそのまま適用すると`"url"` という文字列が存在せず常にマッチしない（＝チェックが機能しない）。そこで今回は `grep '^-  "'` に読み替えて適用したところ、末尾要素にカンマが付与される整形差分（削除ではなく同一URLの再フォーマット）を偽陽性として検出した。`diff <(jq -r '.[]' base | sort) <(jq -r '.[]' new | sort) | grep '^<'` による集合ベースの比較では削除0件を確認しており、実際のデータ削除は発生していない。
- **提案する変更**: プロンプトの「immediately before `git commit`」チェックを、スキーマがフラット配列の場合は `git diff --cached _seen.json | grep '^-  "'`（末尾カンマ差分の偽陽性が起きうる点に要注意）ではなく、`diff <(jq -r '.[]' /tmp/seen-base.json | sort) <(jq -r '.[]' _seen.json | sort) | grep '^<'` の集合ベース比較のみを最終ゲートとして採用するよう明記する。行ベースの grep は JSON 整形の都合で偽陽性が起きやすく、`abort` 判定の根拠としては不適切。
- **優先度**: 中〜高（今回は実害なし・正しく集合ベースの再チェックで誤検知と確認した上でコミットしたが、次回セッションが行ベースチェックのみを信じて不要な `drop detected, aborted` を出す/あるいは逆に見逃すリスクがある）
