## プロンプト改善提案（2件）

### 1. パターン1c判定に「除外の具体例」を追加する
- **対象セクション**: 「パターン1c: 公式機能の検証記事（限定的に単独採用可）」
- **現状の記述**: 「対象は「公式ツールの設定ファイル形式・API に直接関わる検証」に限定する。設計論・運用 Tips・体験記は対象外」
- **提案する変更**: この一文の直後に、境界の具体例を1〜2個追加する。例:「◯（対象内）: 公式ツールの実際のconfigキー・エラーコード・CLIフラグを示す検証。✕（対象外）: 公式ツールの実際のAPI出力フィールドを使っていても、結論が「運用上こうすべき」という一般的Tipsに留まるもの（例: 計測回数を増やして中央値を取る、fail-loudな設計にする）」
- **理由**: 本日、実際のAPI/JSON出力を使っている記事が2件あり、コード例の有無だけでは1c該当性を判断できず、「主眼が設定/APIの検証か、運用上の教訓か」という追加の軸で判定する必要があった。具体例があれば次回セッションでも同じ基準で判定しやすくなる
- **想定リスク**: なし（既存の却下判断を明文化するだけ）
- **優先度**: 低

### 2. Step 5 の commit 直前チェックを「末尾要素のカンマ変更」を除外する形に修正する
- **対象セクション**: 「_seen.json の仕様 > 削除禁止ルール」手順5
- **現状の記述**: `git diff --cached _seen.json | grep '^-  "' && { echo "ERROR: URL deletion in staged diff"; exit 1; }`
- **提案する変更**: 削除行から同一URLの追加行（末尾のカンマ有無だけが違うもの）を除外してから判定する。例: `diff <(jq -r '.[]' /tmp/seen-base.json | sort) <(jq -r '.[]' _seen.json | sort) | grep '^<'` （手順3と同じsort済み比較）を手順5でも再利用し、生の `git diff` grep は使わない
- **理由**: 手順3で既に正確な削除検知ロジックがあるにもかかわらず、手順5は別の（不正確な）ロジックで再チェックしており、末尾要素への追記という最も頻繁なケースで誤検知する。同じロジックを再利用すれば矛盾なく安全性を担保できる
- **想定リスク**: なし（より正確な検知方法に統一するだけ）
- **優先度**: 中（毎日の実行で必ず発生する誤検知のため）
