## 観察した問題（4件）

### 1. `_seen.json` の実ファイル形式がプロンプト仕様と乖離している
- **種類**: プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > スキーマ」節
- **詳細**: プロンプトは `{"version", "updated_at", "entries": [{"url","fetched_at","status"}]}` というオブジェクト形式を規定しているが、リポジトリの実 `_seen.json`（4184件、main HEAD時点）は `["url1", "url2", ...]` という単純な文字列配列。おそらく過去のどこかの実行で実装がスキーマ仕様から逸脱し、以降そのまま踏襲され続けている。
- **影響**: 今回はリポジトリの実形式（flat array）に合わせて4URLを追記した。`status`（adopted/read_skipped/fetch_failed）を保持できないため、「24時間以内の fetch_failed は再試行可」「read_skipped は却下理由付きで再読み込み防止」といった仕様上の区別が実データ上は失われている。
- **再現性**: 継続的（過去のすべての `_seen.json` 更新PRが同じ flat array 形式で行われていると推測されるが、直接の過去 changelog 記載は未確認）

### 2. 標準RSSソースの全トピック網羅が時間内に完了しない

## プロンプト改善提案（3件）

### 1. `_seen.json` のスキーマ記述を実装（flat array）に合わせて更新する
- **対象セクション**: 「`_seen.json` の仕様 > スキーマ」
- **現状の記述**: `{"version": "1.0", "updated_at": ..., "entries": [{"url","fetched_at","status"}]}`
- **提案する変更**: 実ファイルの `["url1", "url2", ...]` 形式に合わせてスキーマ記述を書き換えるか、あるいは逆に実ファイルをオブジェクト形式へ移行するワンショットの移行PRを別途起票する。どちらかに寄せないと、Routine 実行のたびに「仕様通りに解釈すべきか、実データに合わせるべきか」の判断が発生する。
- **理由**: 今回、スキーマ通りに実装すると既存4184件の flat array を破壊的に作り替えることになり「削除禁止ルール」のリスクが高まるため、実データ形式を優先した。プロンプトが実態と異なるスキーマを記述し続けるのは事故のもと。
- **想定リスク**: 移行PRを選ぶ場合、`status` フィールド欠如により過去エントリの `adopted`/`read_skipped`/`fetch_failed` 区別が付けられず、全件を仮に一律ステータスにする必要がある。
- **優先度**: 高

### 2. 標準RSSソースのトピック網羅を「日替わりローテーション」にする
- **対象セクション**: 「標準RSSソース定義（24ソース）」節
- **現状の記述**: Zenn/Qiita/dev.to/Medium 全トピックを毎日フル実施する前提の記述
- **提案する変更**: 例えば「コアトピック（nextjs, react, typescript, testing, security, ai-agent 系）は毎日実施」「残りのトピック（css, i18n, graphql, monorepo 等）は曜日ごとに分割し、週内で一巡させる」というローテーション表をプロンプトに追記する。
- **理由**: 現状の全量前提だと実行のたびに「時間制約・未試行」が大量発生し、それが正常なのか異常なのか changelog を見ても判断しづらい。ローテーション制にすれば「今日担当のトピックが完了しているか」で正常性を判定できる。
- **想定リスク**: ローテーション導入により特定トピックの検知が最大1週間遅延する。ただし現状でも実質的に多くのトピックが「時間制約」で毎回スキップされている可能性があり、実害は変わらないかむしろ可視化される。
- **優先度**: 中

- **優先度**: 高

### 5. `_seen.json` コミット直前チェック（`git diff --cached | grep '^-  "'`）が偽陽性を出した
- **種類**: プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > 削除禁止ルール」Step 5（commit直前の行ベース確認）
- **詳細**: Step 5 の `git diff --cached _seen.json | grep '^-  "'` を実行したところ `https://techblog.zozo.com/entry/screen-analyze-v2` が削除行として検出された。しかし Step 3 のソート済みURL集合比較（`diff <(sort base) <(sort new) | grep '^<'`）では drop 0 件（正しい判定）。原因を調査したところ、このURLはベースファイル内で重複なく1件のみ存在し、新ファイルでも1件のみ存在していた——つまり実際のデータ損失はゼロで、jq の dedupe 処理が別の箇所にあった重複（ベースファイル内の別URLの重複）を1件解消したことで後続行がシフトし、行ベースdiffが「削除+追加」として検出しただけだった。
- **影響**: 実害なし（Step 3 の集合比較で正しく安全性を確認できたため、コミットは正常に完了した）。しかし Step 5 のチェックだけを見ると `_seen.json` にありがちな「URL削除事故」と誤認して不要にコミットを中止しかねない。
- **再現性**: 単発だが、ベースファイル内に重複URLが残っている限り今後も同じ偽陽性が起こり得る

## プロンプト改善提案（4件目）

### 4. `_seen.json` コミット前チェックの Step 5 を集合比較ベースに変更する
- **対象セクション**: 「`_seen.json` の仕様 > 削除禁止ルール」Step 5
- **現状の記述**: `git diff --cached _seen.json | grep '^-  "' && { echo "ERROR: URL deletion in staged diff"; exit 1; }`
- **提案する変更**: 行ベースの grep ではなく、Step 3 と同じソート済み集合比較を commit 直前にも再実行する（`diff <(git show HEAD:_seen.json | jq -r '.[]' | sort) <(jq -r '.[]' _seen.json | sort) | grep '^<'`）。あるいは Step 5 を残す場合は「行削除を検出したら、まずそのURLが新ファイルに存在するか `jq --arg u "$URL" 'index($u) != null' _seen.json` で確認し、存在すれば誤検知として無視する」という一次切り分け手順を追記する。
- **理由**: 現行の Step 5 は「削除された行」と「重複解消による行シフト」を区別できず、ベースファイルに1件でも重複URLが残っていると毎回偽陽性でコミット中止判定になりうる（今回はコミット自体は完了したが、判断に追加調査が必要だった）。
- **想定リスク**: なし。集合比較のほうが Step 3 と一貫性があり、真の削除だけを確実に検出できる。
- **優先度**: 中
