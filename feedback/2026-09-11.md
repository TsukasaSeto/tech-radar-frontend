## 観察した問題（4件）

### 1. `_seen.json` の base 取得で、キャッシュ済み `origin/main` refを使うと既存URLを大量ロストしかける

- **種類**: ツール / プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > 削除禁止ルール」Step 1（`git show origin/main:_seen.json > /tmp/seen-base.json`）
- **詳細**: セッション開始直後（`git fetch` 未実行）の状態で `origin/main` のリモート追跡ブランチは clone 時点のまま古く、実際の GitHub 上の `main`（4184件）より320件少ない（3864件）スナップショットを指していた。手順通りに `git show origin/main:_seen.json` を実行しただけで、このstaleな3864件をbaseにdedupe処理をしてしまい、生成された `_seen.json` は既存320件を欠落させる寸前だった（commit前にdiff検証で偶然気づいた）。手順書自体は「diff検証必須」としているが、diff検証はあくまで「baseに対して」の比較であり、**baseそのものが古ければdiff検証は無意味**という盲点がある。
- **影響**: 実行時点でcommit前に気づいたため実害なし。ただし `git fetch` を挟まない実行では320件のURL誤削除（PR #40と同種の事故）が発生していた可能性が高い。
- **再現性**: 単発（今回のセッションで気づいたのは初めて）だが、`git clone` 直後に手順を素通りする限り**構造的に毎回起こりうる**。

### 2. `_seen.json` の実ファイル形式が、プロンプトが定義するスキーマと一致していない

- **種類**: プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > スキーマ」セクション
- **詳細**: プロンプトは `{version, updated_at, entries: [{url, fetched_at, status}]}` という object スキーマを前提にしているが、実際のリポジトリの `_seen.json` は **URL文字列だけのフラット配列**（4184件、`status` フィールドなし）。このため、プロンプトが定義する `adopted` / `read_skipped` / `fetch_failed` の3ステータス運用（特に「`read_skipped` を毎日読み直さないために記録する」「`fetch_failed` は24時間後に再試行可能」というロジック）は、**実ファイル上では一切表現できない**。今回はこの矛盾を踏まえ、実ファイルの慣習（URL文字列の配列）に合わせてURLのみをappendした。
- **影響**: 個別記事を「読んだが採用しなかった」場合に `read_skipped` として記録できないため、次回以降の実行で同じ低品質記事を重複して読みに行くコストが発生しうる（今回は本文を個別取得した記事が全て採用に至ったため実害なし）。
- **再現性**: 継続的（スキーマとファイル実体の乖離はおそらく複数回のRoutine実行を経ても解消されていない）。

## プロンプト改善提案（4件）

### 1. `_seen.json` base取得の直前に `git fetch origin main` を必須手順として明記する
- **対象セクション**: `_seen.json` の仕様 > 削除禁止ルール > 1. 現在の `main` 状態を取得
- **現状の記述**: `git show origin/main:_seen.json > /tmp/seen-base.json`
- **提案する変更**:
  ```bash
  git fetch origin main --quiet
  git show origin/main:_seen.json > /tmp/seen-base.json
  # baseの件数を明示的にログ出力し、明らかに小さすぎないか目視確認する
  echo "base件数: $(jq 'length' /tmp/seen-base.json)"
  ```
- **理由**: 今回、`git fetch` を挟まなかったために stale な `origin/main` を参照し、320件のURL欠落を起こしかけた。`git fetch` を明示コマンドとして手順に組み込まない限り、実行環境（cloneのタイミング）によって再発する。
- **想定リスク**: なし（`git fetch` は読み取り専用操作）
- **優先度**: 高

### 2. `_seen.json` のスキーマ記述を実ファイル形式（フラット配列）に合わせて修正するか、実ファイルをobjectスキーマへ移行する
- **対象セクション**: `_seen.json` の仕様 > スキーマ
- **現状の記述**: `{version, updated_at, entries: [{url, fetched_at, status}]}` という object スキーマ
- **提案する変更**: 2つの選択肢のどちらかを人間が決定する必要がある:
  - (a) プロンプトのスキーマ定義を「URL文字列のフラット配列」に修正し、`read_skipped` / `fetch_failed` ステータス運用の記述を削除する（実態に合わせる、変更コスト小）
  - (b) 次回以降、実ファイルを object スキーマへ一括移行し、既存4184件のURLは `status: "adopted"`（実際のステータス不明のため便宜上）として移行する（プロンプトの意図を活かす、変更コスト中）
- **理由**: 現状はプロンプトを読んだ実行者（Claude）が実ファイルとの乖離に気づいて独自に読み替える必要があり、乖離に気づかなければ壊れたJSONをコミットするリスクがある。
- **想定リスク**: (b) を選ぶ場合、既存の `read_skipped`/`fetch_failed` の実態不明URLに誤った `status` を付与してしまう可能性がある
- **優先度**: 高
