### 1. このセッションは本来「ローカル Claude Code セッション（PR取り込み用）」のはずが、cloud Routine 本体の処理を代行実行した

- **影響（数値）**: Stripe Engineering 1ソースが取得失敗。
- **再現性**: 単発（今回のスケジュール設定に起因する可能性が高い。過去 changelog にはこの種の記述なし）

### 3. `_seen.json` の実データ形式がプロンプトのスキーマ定義と一致していない
- **種類**: プロンプト記述
- **発生箇所**: 「`_seen.json` の仕様 > スキーマ」セクション
- **詳細**: プロンプトは `{version, updated_at, entries: [{url, fetched_at, status}]}` という構造を定義しているが、実際の `_seen.json` は単純な URL 文字列の配列（3,896件、`status` フィールドなし）。一方で同じプロンプト内の「削除禁止ルール」セクションの jq コマンド例（`. + $new | reduce ...`）はこの配列前提で書かれており、実データと整合している。
- **影響**: `status: adopted / read_skipped / fetch_failed` の区別が実データ上は表現できないため、今回は "削除禁止ルール" セクションの手順（配列への append + dedupe + diff検証）に従い、URL のみを追記した。fetch_failed の24時間後再試行判定など、status に依存する仕様は実運用ではそもそも機能していない可能性がある。
- **提案する変更**: スキーマ定義セクションを実データ（フラット配列）に合わせて修正するか、実際に `{url, fetched_at, status}` 形式への移行を別 Routine で行うかを明確化する。
- **優先度**: 中

## プロンプト改善提案（2件）

### 1. 「時間制約・未試行」を選ぶ判断基準を明文化する
- **対象セクション**: 「段階1をスキップするソース」直後の注記
- **現状の記述**: 「ソース単位で時間内に着手できなかった場合は…失敗扱いにしない」とあるが、「時間内」の基準（残り何ソース時点で打ち切るか等）が定義されていない
- **提案する変更**: 「公式6 + 国内9 + 海外4 + Stripe を優先して全件着手し、その後コミュニティ系トピックを新着頻度の高い順（nextjs/react/typescript/aiagent/claudecode/security を最優先）に着手する。1回の実行で着手できるコミュニティ系フィード数の目安は◯件」のように優先順位と目安件数を明記する
- **理由**: 今回、優先順位を実行者（このセッション）の裁量で決めたため、日によって「どのトピックが手薄になるか」がばらつくリスクがある
- **想定リスク**: 優先順位を固定すると、優先度の低いトピック（例: i18n, monorepo）の新着が恒常的に見逃される
- **優先度**: 高

### 2. スケジュールされたプロンプト本文に、実行環境が `tech-radar-curator-env` であることの事前確認ステップを入れる
- **対象セクション**: 「実行環境の前提」
- **現状の記述**: 「このRoutineは custom env (tech-radar-curator-env) で実行されることを前提とする」と書かれているが、実行前にその前提を検証する手順がない
- **提案する変更**: Step 1 の前に「現在の実行環境が `tech-radar-curator-env` かどうかを確認し、異なる場合は allowlist の差異（特に `stripe.com` のリダイレクト先 `stripe.dev` 等）を feedback に明記した上で続行する」という一文を追加する
- **理由**: 今回のセッションは異なる実行環境（GitHub MCP スコープドセッション）で本プロンプトを受け取っており、環境差異に起因する失敗（Stripe）が発生した
- **想定リスク**: 確認ステップが増えることで実行時間がわずかに増える
- **優先度**: 中
