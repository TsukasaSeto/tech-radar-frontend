### 強化 (3件)

1. `practices/security/xss.md` - Rule #2（`href`/`src` への未検証入力、SSRF対策節）を強化
   - 出典: https://github.com/OWASP/CheatSheetSeries/commit/e2d422148bebd737e7d85e45347ae85ae5e878ba （OWASP CheatSheetSeries commit #2412） ※2026-09-15に実際にfetch成功
   - 引用: > "Match the host against an allowlist, and build the request yourself...compare that value against an explicit allowlist of permitted destinations, then build the request from the entry that matched" (セクション "SSRF: validate with an allowlist, not with a parser")
   - 判定根拠: Pattern 1（公式ソース: OWASP公式CheatSheetSeriesリポジトリのコミット）。既存ルールは `new URL()` によるパーサー正規化止まりだったが、OWASP側がパーサー依存の検査ではなく「許可リストに一致した値からリクエストを組み立て直す」方式・「パーサー間でホスト解釈が食い違うURLは判定せず拒否する」方式を明文化したため、同一趣旨の既存ルールへの強化根拠として統合（新規ルール化はせず）。

2. `practices/security/secret-management.md` - Rule #1（`NEXT_PUBLIC_` プレフィックス）を強化
   - 出典: https://zenn.dev/y3chi5z/articles/next-public-env-baked-at-build （Zenn y3chi5z） ※2026-09-15に実際にfetch成功
   - 引用: > "NEXT_PUBLIC_ で始まる環境変数は、ビルドのときにソースコードへ直接インライン化されます" (セクション "原因")
   - 判定根拠: Pattern 1c（非公式記事だが、Next.jsの`NEXT_PUBLIC_`のビルド時インライン化という公式挙動を、Vercelでの実際の事故と`vercel redeploy`という公式CLIコマンドで具体的に検証）。既存ルールは境界の明示のみでローテーション時の再デプロイ必要性に触れていなかったため、強化として統合。

3. `practices/performance/image-optimization.md` - Rule #3（OGP画像の`next/og`動的生成）を強化
   - 出典: https://zenn.dev/cosoado/articles/nextjs16-image-cache-ttl-4h-ogp-stale （Zenn cosoado） ※2026-09-15に実際にfetch成功
   - 引用: > "v16.0.0 では「アップストリームに Cache-Control を返さない画像が多く、60s では無駄な再バリデーションが多すぎる」という理由でデフォルトが 14,400s に変更された" (セクション "minimumCacheTTL とは")
   - 判定根拠: Pattern 1c（非公式記事だが、Next.js 16.0.0の`images.minimumCacheTTL`デフォルト変更という公式の具体的バージョン変更を、`next.config.ts`の実設定コードで検証）。既存ルールのバージョン注記を「Next.js 13+」から「Next.js 16+」に更新し、`/_next/image`経由時の落とし穴と対処法（`minimumCacheTTL`明示指定）を追記する強化として統合。
